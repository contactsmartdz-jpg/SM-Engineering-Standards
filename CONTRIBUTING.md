# Contributing

Thank you for helping improve a language-agnostic, project-independent engineering standard.

## What belongs here
- Clear, testable engineering rules with general applicability.
- Reasoned examples using synthetic, non-sensitive information.
- Reusable templates and vendor-neutral adoption guidance.
- Corrections to ambiguity, contradictory obligations, or broken references.

## What does not belong here
- Customer data, credentials, private repository links, internal deployment details, or unpublished business decisions.
- Rules requiring one commercial provider, programming language, framework, or organization structure without a broadly justified reason.
- AI-generated claims or citations that cannot be verified.

## Contribution process
1. Check whether the change duplicates an existing rule.
2. Open an issue or pull request describing the problem, affected rule IDs, proposed language, alternatives, and compatibility impact.
3. Use MUST/SHOULD/MAY terms consistently and explain how the requirement can be verified.
4. Update navigation, templates, and adoption guidance if a new control changes usage.
5. Run the repository's documentation validation before requesting review.
6. Treat security-sensitive changes and changes to requirements as substantive, requiring independent review.

## Rule ID policy
Once published in a stable release, an ID should remain stable. If a rule is replaced, document its successor and migration guidance rather than silently recycling the ID.

## Releases
The default branch may contain drafts. Tags document what adopters should pin; a draft is not a stable v1.0 release. Breaking obligations require a major-version release after 1.0.
